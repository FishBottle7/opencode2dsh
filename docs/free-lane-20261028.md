# Opt-in Bun transport for the 2026-10-28 free-lane refusal (#108)

`429 FreeUsageLimitError` can describe different refusals. In the tested Windows
environment, an official OpenCode 2.2.0 request succeeded on the same machine and
network while the plugin's minimal request was refused. Changing the User-Agent
alone did not recover it. This is evidence for a compatibility problem in this
environment, not proof that every 429 is a client check or that real quota limits
can be removed.

## Enable

Install Bun yourself from its official distribution, then opt in through the
plugin's ordinary configuration. No runtime is downloaded, installed globally,
or bundled by this feature. Bun 1.4.4 was tested; other versions are unverified.

```yaml
- id: opencode2dsh
  name: '@opencode2dsh/dsh-plugin'
  config:
    bunTransport:
      enabled: true
      bunPath: /absolute/path/to/bun
      clientVersion: 2.2.0
```

On Windows, a path such as `C:/tools/bun.exe` is accepted directly, including
spaces; it is never interpolated into a shell command. Restart/reload the plugin
after changing ordinary configuration. Set `enabled: false` to return to the
existing transport.

This mode requires `ipPool.enabled: false`. Bun cannot use the process's Node
Undici dispatcher. The guard reads the live pool state on every request and
returns an explicit error instead of silently bypassing a configured pool.

## What changes

- Only anonymous inference POSTs started by this adapter's SDK are selected.
  Catalog fetches, unrelated providers, custom hosts and unscoped concurrent
  requests keep their existing fetch. The scoped hook is reference counted and
  restored on final disposal where it is still the installed hook.
- One short-lived Bun process performs the request with native `fetch`. It has
  no tool executor, local HTTP listener, credential discovery or login flow.
- Chat requests use `/inference/openai/v1/chat/completions`, as listed by the
  official v2 model catalog. The UA uses the v2 `opencode/latest/<version>/cli`
  format. Session IDs remain stable under the existing conversation mapping.
- A small `<env>` block is added only when the system/developer instructions do
  not already include one. `Working directory: .` is relative to the host's
  workspace instructions, not a new tool working directory. Existing DSH
  instructions, messages, images, tools and choices remain intact. No official
  OpenCode persona, tool instructions or full system prompt is copied.
- The stdin/stdout transport preserves streaming bytes and upstream status and
  retry headers. It accepts only `Bearer public`, an exact HTTPS origin and a
  fixed inference path allowlist. Cookies, SDK telemetry headers and response
  cookies are omitted. Redirects are refused. Request bodies and credentials are
  neither logged nor written to disk.
- Abort, consumer cancellation, header/body-idle timeouts and plugin disposal
  terminate owned subprocesses. Reinstalling or disabling the feature does not
  change the user's separately installed Bun runtime.

The SDK still creates and interprets native tool calls. DSH remains responsible
for executing tools and returning their results; this is not an ACP session or
an external autonomous OpenCode agent.

## Controlled observations, 2026-10-28

The probes used only a fixed diagnostic prompt and anonymous `public`, with no
personal API key, previous login or user conversation.

| Request | Result |
| --- | --- |
| Unmodified 0.3.14, GLM and MiMo | 429 |
| v2 UA only | 429 |
| Official OpenCode 2.2.0, isolated state | 200, `OK` repeatedly |
| Official payload forwarded with Node fetch/HTTPS or Undici with HTTP/2 enabled | 429 |
| Same official payload forwarded with Bun native fetch | 200, `OK` |
| Plugin body + official headers, Bun | 429 |
| Official body + plugin headers with v2 UA, Bun | 200 |
| Plugin body + only the short environment block, Bun/v2 format | 200, `OK` |
| Local patched adapter, GLM and MiMo | normal `stop` responses |
| Local patched adapter, diagnostic host tool then tool-result continuation | `tool-calls`, then the expected result |

The end user subsequently tested every free model individually and confirmed they all worked. The scripted reproduction below remains limited to GLM, MiMo and a host tool/result round trip. These results do
not identify the server implementation, an exact TLS fingerprint rule, or a
universal acceptance condition. In particular, enabling HTTP/2 in Node alone did
not recover the tested request.

Windows x64 was tested live. macOS/Linux, other Bun releases, Responses models,
image requests and arbitrary proxy setups were not live verified. Automated
tests cover Responses instruction preservation and multimodal payload
preservation, but that is not a claim of live upstream compatibility.
